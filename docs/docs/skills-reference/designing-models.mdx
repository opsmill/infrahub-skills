title: Model Designer
---

Skill: `infrahub-designing-models`

The Model Designer works out what to model before any schema exists. It reads the diagrams, spreadsheets or documents you have, then interviews you one question at a time: first why the data matters, then what is delivered or ordered, and only then the data itself. Each question comes with a recommended answer and the reason for it. The result is a design brief that the managing skills build from: the [Schema Manager](./managing-schemas.mdx) first, then the skill for each other artifact the brief lists.

## When to use

- You know what is broken or missing, but not yet which node kinds you need
- You have diagrams, inventory exports or a requirements document to turn into a design
- A request spans several domains, such as a fiber plant, DWDM channels and a wavelength service, and needs to be split
- A design brief exists and needs another feature or a changed decision

## What it produces

`design-brief.md`, in your repository's existing design-document location or `docs/designs/<design-slug>/` by default. It holds:

- **Summary**: the problem, the intended outcome and what is not decided yet, in three to five sentences
- **Inputs**: each file you provided and what was taken from it
- **Business and service**: who uses the data, the incident it prevents, what is ordered, and the service lifecycle
- **Reference design**: the closest OpsMill demo or solution to build from, such as `infrahub-demo-sp` for an L3VPN service, what the design follows from it, and where it differs
- **Features**: one row per feature in build order, with the artifacts each one needs (schema, objects, generator, check, transform, menu), its dependencies, and a handoff that names the brief and the feature ID, for any downstream workflow
- **Data model sketch**: for the first feature, each node kind with how it is identified, its key attributes, its peers, its source of truth, its owner, and where each fact came from
- **Mechanisms**: a table of each behavior and what delivers it (a generator, a check, a transform, a computed attribute, a resource pool or a schema constraint), with what drives it, what it produces and when it runs, so the skill that builds it has the decisions it needs
- **Plan map and model map**: two Mermaid diagrams drawn from the Features table and the sketch, showing the build order and how the F1 node kinds relate
- **Next steps**: a short numbered list for you to follow, worded for the workflow your repository already uses: spec-kit, another planning setup, or the managing skills
- **Decision log and open items**: every decision tagged as stated by you, accepted from a recommendation, or open, and every unknown with who owes the answer

It writes no schema YAML.

## Example prompts

- "We want our L3VPN service in Infrahub. Where do we start?"
- "Here's our sites spreadsheet and the out-of-band diagram. What should the model look like?"
- "Model our whole optical network: fiber plant, DWDM channels and customer wavelengths"
- "Add a peering feature to our existing design brief"

## Key rules enforced

- **One question at a time, with a recommendation**: each message is a single question with two to four options, one marked as recommended, and the basis for it with its strength
- **A draft before the details**: after a few business and service questions, you see a draft of the model with each guess marked and two or three sample objects built from your own data, and the data questions go to the guesses that matter most. Nothing in the draft is invented: every guess comes from your files, your answers, a Marketplace schema that covers the node kind, the reference design or an Infrahub default, and any other cell stays unknown and becomes a question
- **A scenario walkthrough**: before the brief is confirmed, one event such as an order or a decommission is walked through the model to find missing peers or unclear deletes
- **Grounded in the managing skills**: each data question names the schema or best-practice rule its answer feeds, such as uniqueness scope, what happens on delete, or a resource pool instead of hand allocation, and no guess reaches the brief unconfirmed
- **Start from a worked example and published schemas**: the brief names the closest OpsMill reference design and the Marketplace schemas it builds on, matched against each node kind from the whole catalog, or says why none fits. When the catalog cannot be searched, for example without network access, the brief says so and keeps it as an open item
- **Every generator, check and transform has its decisions**: each one the features list has a Mechanisms row saying what drives it, what it produces and when it runs, and a rule the schema can enforce, such as uniqueness, is a schema constraint rather than a check
- **Next steps in order**: open items first, then each feature after the features it depends on
- **Answers that land later**: each open item names the features it affects, so an answer given later updates the right features and flags those already specified or built
- **Your files are evidence**: every file you provide is listed in the brief, and model rows built from it name it as their source
- **Split before modelling**: a scope that covers several domains or many node kinds is split into ordered features, and only the first is modelled in depth
- **No invented values**: a node kind's identity, source of truth or owner is either answered or recorded as an open item
- **Provenance on every decision**: the brief separates what you decided from what you accepted on the skill's recommendation
- **Maps that match their tables**: the plan map and the model map show exactly the features, dependencies, node kinds and peers in their tables, nothing more

## Common mistakes it catches

- Writing a schema before anyone has asked what service it models
- A model built around devices with no service object
- Two systems both treated as the source of truth for the same data
- "Sensible defaults" that look decided but were never confirmed
- A generator chosen for a value that a computed attribute on the same node would give

## Example: an L3VPN service

You ask: "We want our L3VPN service in Infrahub. Where do we start?" You attach `vpn-customers.xlsx`, an export with one row per VPN and its sites.

### The interview

Each message is one question. The skill reads your file first, so the first business question already uses what is in it:

```markdown
**Q1 (business):** Which task fails today because VPN data is wrong or missing?

- A. Provisioning: a new site gets a route distinguisher that is already in use  **(Recommended)**
- B. Troubleshooting: nobody can tell which PE serves which customer site
- C. Billing: VPNs stay billed after they are decommissioned

**Basis:** vpn-customers.xlsx has duplicate values in its rd column (strong)
```

You answer "A". Later, a service question separates what the customer orders from what the network team derives:

```markdown
**Q3 (service):** What does the customer order?

- A. One VPN, with sites added to it over time  **(Recommended)**
- B. Each site as its own order, grouped into a VPN afterwards
- C. Both, depending on the customer

**Basis:** every row in vpn-customers.xlsx is one VPN with a site list (strong)
```

You answer "A, but the route targets are ours to choose, not the customer's". The skill records the first half as an accepted recommendation and the second as your own decision.

Before the data questions, the skill shows a draft of the model built from your file and the closest reference design, `infrahub-demo-sp`, which models L3VPN services with their sites. Each guess is marked `(guess)`, and the next questions go to the guesses that change the design most. Only the rows that changed come back after each answer:

```markdown
| Feature | Node kind | Identified by | Peers (cardinality) | Owner |
| --- | --- | --- | --- | --- |
| F1 | L3Vpn | customer + vpn_name (guess) | VpnSite (many) | Network team (guess) |
| F1 | VpnSite | vpn + site_code (guess) | L3Vpn (one) | (guess) |
```

### The brief

The request covers the VPN service and the allocation of route distinguishers and route targets, so the skill splits it into two features and models only the first in depth. The brief, `docs/designs/l3vpn-service/design-brief.md`:

````markdown
## Summary

New VPN sites sometimes get a route distinguisher that is already in use, because route distinguishers are kept by hand in the customer export. The outcome is one object per ordered VPN with its sites, loaded from that export, and route distinguishers and route targets allocated from pools so they cannot clash. Not decided yet: who owns site records once a VPN is live (O1).

## Inputs

| File | Taken from it |
| --- | --- |
| vpn-customers.xlsx | One row per VPN: customer and vpn_name identify it, site_code identifies each site, and the rd column has duplicate values |

## Business

The provisioning team uses the data when they add a site to a VPN. It prevents a new site getting a route distinguisher that another VPN already uses. Out of scope: billing and troubleshooting.

## Service

The customer orders one VPN and adds sites to it over time. The customer decides the VPN name and bandwidth, its sites, and each site's access type. The network team derives the route distinguishers and chooses the route targets. Lifecycle: ordered, active, decommissioned; the network team moves a VPN between them.

## Reference design

Closest: infrahub-demo-sp
Reused: the service-with-sites pattern (L3Vpn and L3VpnSite, called VpnSite in this brief)
Different: route distinguishers and route targets come from pools, not from the order
Marketplace: infrahub/base-schemas (locations and devices behind each VpnSite)

## Features

| ID | Feature | Intent | Scope boundary | Artifacts | Depends on | Status | Handoff |
| --- | --- | --- | --- | --- | --- | --- | --- |
| F1 | VPN service | One object per ordered VPN, with its sites | L3Vpn, VpnSite | schema, objects | - | planned | Design and implement the L3Vpn and VpnSite model, then populate it from the customer export, as designed in F1 of docs/designs/l3vpn-service/design-brief.md. |
| F2 | RD and RT allocation | No duplicate distinguishers or targets | RD pool, RT pool | schema, objects | F1 | planned | After F1, design the RD and RT pools and populate the initial allocations, as designed in F2 of docs/designs/l3vpn-service/design-brief.md. |

  schema, objects"]
  F2["F2 RD and RT allocation
  schema, objects"]
  F1 --> F2
```

## Data model sketch

| Feature | Node kind | Identified by | Key attributes (value class) | Peers (cardinality) | Source of truth | Owner | Evidence |
| --- | --- | --- | --- | --- | --- | --- | --- |
| F1 | L3Vpn | customer + vpn_name | bandwidth (stated) | VpnSite (many) | Infrahub | Network team | vpn-customers.xlsx:vpn_name |
| F1 | VpnSite | vpn + site_code | access type (stated) | L3Vpn (one) | Infrahub | open: O1 | vpn-customers.xlsx:site_code |

```

## Mechanisms

| Feature | Behavior | Mechanism | Driven by | Produces | Runs when | Why |
| --- | --- | --- | --- | --- | --- | --- |
| F1 | No two VPNs of one customer share a name | schema constraint | L3Vpn | uniqueness on customer and vpn_name | every change | the schema enforces it without code |
| F2 | Each VPN gets a route distinguisher and route targets | resource pool | L3Vpn | an RD and RT values | a VPN is created | no hand allocation, no duplicates |

## Decision log

| # | Decision | Tag | Basis |
| --- | --- | --- | --- |
| 1 | The customer orders one VPN, and sites are added to it | recommended | Every row in vpn-customers.xlsx is one VPN with a site list (strong) |
| 2 | The network team chooses route targets, not the customer | stated | |
| 3 | Who owns site records once a VPN is live | open | O1 |

## Open items

- O1: Who owns site records once a VPN is live? (owner: unknown, network or service desk; affects F1)

## Next steps

1. Settle O1 with the network team and the service desk.
2. Build F1 VPN service: run the Schema Manager, then the Object Manager to load the VPNs from the customer export.
3. When F1 is loaded, build F2 RD and RT allocation with the Schema Manager and the Object Manager.
````

### Next steps in a spec-kit repository

The Next steps above are for a repository with no specification or planning workflow: each artifact in a feature's `Artifacts` cell goes to its managing skill, in the listed order. Here F1 lists `schema, objects`, so the [Schema Manager](./managing-schemas.mdx) writes the L3Vpn and VpnSite schema, then the [Object Manager](./managing-objects.mdx) loads the VPNs from the customer export.

When the repository has a `.specify/` folder, the skill words each feature's step as a `/speckit.specify` prompt that carries the feature's `Handoff` cell:

```markdown
## Next steps

1. Settle O1 with the network team and the service desk.
2. Specify F1 VPN service: `/speckit.specify Design and implement the L3Vpn and VpnSite model, then populate it from the customer export, as designed in F1 of docs/designs/l3vpn-service/design-brief.md.`
3. When F1 is built, specify F2 RD and RT allocation: `/speckit.specify After F1, design the RD and RT pools and populate the initial allocations, as designed in F2 of docs/designs/l3vpn-service/design-brief.md.`
```

The handoff names the brief and the feature ID, so `/speckit.specify` reads the sketch, decisions and open items from the brief rather than from one sentence. [Spec-driven development](../spec-driven-development.mdx) shows the rest of that flow. With another specification or planning setup, each step gives the same `Handoff` cell to that setup instead.

## Coming back with an answer

Open items often get answered days later. Run the Model Designer again on the same brief with the answer, for example "O1 is settled: the service desk owns site records, see docs/designs/l3vpn-service/design-brief.md". Each open item names the features it affects, so the skill:

- records the answer as your decision and fills in the cells that waited on it
- updates every affected feature that is still `planned`
- does not silently rewrite a feature already `specified` or `built`: it notes the change and adds a next step to re-specify it, or to change the loaded schema with the [Schema Manager](./managing-schemas.mdx), which handles the migration
- checks the scope again if the answer adds node kinds, giving any new feature the next ID

It then tells you which features the answer changed.

## Using it with your workflow

The brief does not assume a particular framework. Paste each feature's handoff into your existing specification, planning, ticketing or implementation workflow in dependency order, together with the brief it names. The handoff names the brief and the feature ID, and the workflow reads the details from the brief. For a spec-driven flow, use the handoff as the input to its Specify step. See [Spec-Driven Development](../spec-driven-development.mdx).

## What it does not do

The Model Designer stops at the brief. It does not:

- **Write schema YAML, object files or code.** Each artifact goes to the skill named in [From artifact to skill](#from-artifact-to-skill), in the order of the brief's Next steps.
- **Load anything into Infrahub or run the other skills.** It points to the next step and stops.
- **Build integrations with other systems.** When another system, such as NetBox, is the source of truth for a node kind, the brief records that system and whether Infrahub reads from it or writes to it. It does not create [infrahub-sync](https://docs.infrahub.app/sync/) adapters or mappings, API integrations or webhooks, and no skill in this plugin does. infrahub-sync is a separate product.
- **Query a running Infrahub instance.** It reads your repository and the files you give it, plus the Marketplace catalog and the list of OpsMill demos when it has network access.
- **Download Marketplace schemas or copy a reference design's schema files.** It names the published schemas the design builds on; the [Schema Manager](./managing-schemas.mdx) fetches them with `infrahubctl marketplace get`.
- **Model every feature in depth at once.** After a split, only F1 has rows in the data model sketch. Run it again on the same brief to add a later feature.
- **Resume an interview in a new session.** Nothing is saved until the brief is written. If you stop earlier, continue the same Claude Code conversation (`claude --continue`), or start again and give your earlier answers up front.
